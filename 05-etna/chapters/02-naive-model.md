Наивный прогноз — простейшая отправная точка для сравнения моделей. Его идея: **для будущего использовать одно из
последних известных значений ряда**, не пытаясь отдельно оценить тренд или сезонность. В ETNA для этого есть
`NaiveModel`.

В этой главе разбираем, как устроен `NaiveModel`, что именно задаёт параметр `lag`, почему важно соотношение
`lag` и горизонта прогноза, а также как оценивать качество на отдельных сегментах и на всей выборке.

Исполняемый код, полные графики и сохранённые результаты экспериментов — в
[исходном ноутбуке](../notebooks/02-naive-model.ipynb).

## 1. Теория

### 1.1 Идея наивного прогноза

В классическом варианте `lag=1` наивный прогноз использует последнее доступное наблюдение как прогноз будущего:

\[
\hat{y}_{T+h} = y_T
\]

Здесь \(T\) — последняя дата обучающей выборки, \(h\) — шаг прогноза. При таком варианте все точки горизонта
получают одно и то же значение: прогноз превращается в горизонтальную линию.

Это простейший baseline: он не моделирует тренд, сезонность или другие закономерности. Зато его легко понять и
полезно использовать как точку отсчёта: более сложная модель должна показать, что действительно умеет лучше
простого переноса последнего значения.

### 1.2 `NaiveModel` и `SeasonalMovingAverageModel`

В ETNA `NaiveModel` — обёртка над `SeasonalMovingAverageModel` с фиксированным параметром `window=1`. Изменить
размер окна через `NaiveModel` нельзя: модель всегда использует **ровно одну точку** на выбранном сдвиге.

Поэтому `NaiveModel(lag=1)` — классический наивный прогноз: берётся последнее известное значение. Но при
`lag > 1` модель использует не последнее наблюдение, а значение на заданное число шагов раньше.

### 1.3 `lag`, `context_size` и горизонт прогноза

`lag` — это переименованный параметр `seasonality` родительского `SeasonalMovingAverageModel`. В контексте
`NaiveModel` он задаёт **смещение назад по временной сетке**, а не количество значений для усреднения.

Например:

- `lag=1` — значение за один шаг до прогнозируемой точки;
- `lag=3` — значение за три шага;
- `lag=7` на дневных данных — значение за семь дней до прогнозируемой точки;
- `lag=24` на часовых данных — значение за 24 часа до прогнозируемой точки.

При `window=1` модель смотрит только на одну точку с этим смещением. Она не усредняет последние `lag` наблюдений.
И слово `seasonality` здесь не означает, что модель сама обнаруживает календарную сезонность: ей заранее задают,
на какое расстояние назад смотреть.

У модели есть несколько связанных параметров и методов:

| Параметр / метод | За что отвечает |
|---|---|
| `model.context_size` | Сколько прошлых точек нужно модели для прогноза. Для `NaiveModel` это `window × lag = lag`. |
| `make_future(future_steps=...)` | Сколько будущих временных точек подготовить. Это горизонт прогноза. |
| `make_future(tail_steps=...)` | Сколько последних исторических точек добавить в будущий датасет как контекст. Обычно передаём `model.context_size`. |
| `forecast(prediction_size=...)` | Сколько последних временных меток датасета нужно заполнить прогнозом. Обычно это тот же горизонт. |

Типичный порядок работы:

```python
from etna.models import NaiveModel
from etna.metrics import SMAPE

HORIZONT = 14

model = NaiveModel(lag=HORIZONT)
model.fit(train_ts)

future = train_ts.make_future(
    future_steps=HORIZONT,
    tail_steps=model.context_size,
)

forecast = model.forecast(
    ts=future,
    prediction_size=HORIZONT,
)

metric = SMAPE()(y_true=test_ts, y_pred=forecast)
```

В исходном ноутбуке `forecast` изменяет `future` на месте: после вызова `model.forecast(...)` тот же объект уже
содержит рассчитанные значения `target` на будущем горизонте.

### 1.4 Золотое правило: `lag ≥ horizon`

При многошаговом прогнозировании модель может использовать собственные предыдущие предсказания для расчёта
следующих. Это рекурсивный прогноз. Если ранняя точка предсказана неточно, ошибка может перейти в следующие
точки и повлиять на весь оставшийся горизонт.

Для рассматриваемой схемы `NaiveModel` полезно правило:

\[
\boxed{\text{lag} \geq \text{horizon}}
\]

Если `lag` меньше горизонта, после первых шагов модель начинает обращаться к значениям, которые сама же
предсказала. Если `lag` не меньше горизонта, для всех точек прогноза можно использовать только исторические
факты из обучающей выборки.

Это **условие, позволяющее избежать рекурсивного использования прогноза в пределах выбранного горизонта**, а
не гарантия минимальной ошибки. Как покажет эксперимент, `lag`, который удовлетворяет правилу, всё ещё нужно
подбирать и сравнивать на отложенном периоде.

### Задание 2. Сравниваем `lag` и проверяем золотое правило

В ноутбуке горизонт прогноза задан равным 14 дням. Последние 14 дней каждого ряда откладываются в тест,
всё предшествующее используется для обучения:

```python
HORIZONT = 14

train_ts, test_ts = orders_sample_ts.train_test_split(
    test_size=HORIZONT
)
```

Далее для каждого значения `lag` модель обучается на `train_ts`, получает исторический контекст через
`make_future`, строит прогноз и оценивается по `SMAPE`:

```python
def get_forecast(lag, horizont=HORIZONT, train=train_ts, test=test_ts):
    model = NaiveModel(lag=lag)
    model.fit(train)

    future = train.make_future(
        future_steps=horizont,
        tail_steps=model.context_size,
    )

    forecast = model.forecast(
        ts=future,
        prediction_size=horizont,
    )

    metrics = SMAPE()(y_true=test, y_pred=forecast)

    plot_forecast(
        forecast_ts=forecast,
        test_ts=test,
        train_ts=train,
        n_train_samples=horizont,
    )

    return forecast, metrics
```

> **Нюанс исходного ноутбука:** в формулировке задания предлагается взять один юнит, однако фактически
> `train_test_split` и `get_forecast` применяются к `orders_sample_ts` сразу с двумя сегментами. Поэтому
> сохранённые метрики ниже приведены отдельно для обоих юнитов.

Условие `lag ≥ horizon` также выполняется, но ошибка выше, чем при `lag=14`. Значит, золотое правило задаёт
нижнюю границу для сдвига, а не утверждает, что чем больше `lag`, тем лучше прогноз.

**Вопрос:** почему при `lag=1` прогноз — горизонтальная линия, а при `lag=3` повторяется трёхточечный рисунок?

:::{dropdown} Ответ
При `lag=1` модель каждый раз берёт значение за один шаг до прогнозируемого. Первый прогноз равен последнему
факту, а следующие шаги используют это же предсказанное значение. Поэтому получается постоянная линия.

При `lag=3` модель берёт значения с шагом в три точки. Первые три прогнозируемые точки опираются на историю,
а затем при горизонте 14 дней модель начинает повторно использовать свои предсказания. На графике возникает
циклическое повторение трёхточечного шаблона.
:::

**Вопрос:** означает ли `lag ≥ horizon`, что нужно выбирать максимально большой `lag`?

:::{dropdown} Ответ
Нет. Правило говорит только о том, что в пределах горизонта прогноз не должен опираться на предыдущие
предсказания. Оно не гарантирует, что выбранные исторические значения будут похожи на будущее.

В эксперименте `lag=14` оказался лучше `lag=19` для обоих сегментов: при `lag=19` значения берутся из более
далёкого исторического фрагмента, который хуже описывает тестовый период. Поэтому среди вариантов,
удовлетворяющих правилу, всё равно нужно сравнивать качество на отложенной выборке.
:::

### Задание 3. Сравниваем качество по сегментам и в целом

Для варианта `lag=HORIZONT=14` метрика считается отдельно по каждому сегменту. Затем `SMAPE(mode="macro")`
усредняет полученные значения арифметически:

\[
SMAPE =
\frac{2 \cdot 100\%}{n}
\sum_{i=1}^{n}
\frac{|y_i - \hat{y}_i|}{|y_i| + |\hat{y}_i|}.
\]

- Сначала ошибка рассчитывается для каждой точки тестового горизонта, затем усредняется по точкам — отдельно
  для каждого сегмента (`mode="per-segment"`, режим по умолчанию).
- Диапазон метрики — от `0%` (идеальный прогноз) до `200%`.
- Если и факт, и прогноз равны нулю, знаменатель равен нулю; реализация защищает вычисление с помощью `eps`.
- `mode="macro"` не пересчитывает ошибку по объединённым значениям. Он берёт значения `per-segment` и
  усредняет их арифметически по сегментам.

Результаты для двух юнитов:

| segment | PickReason | SMAPE |
|---|---|---:|
| `70650540` | typical (p25) | 11.26 |
| `a6dffdeb` | busier (p75) | 6.93 |
| **Macro average** | **среднее по двум сегментам** | **9.09** |

**Как читать эти значения:** `SMAPE=11.26` означает, что средняя симметричная процентная ошибка на тестовом
горизонте для typical-юнита составила 11.26%; для busier-юнита — 6.93%. Чем меньше значение, тем точнее
прогноз. Это не то же самое, что обычная средняя абсолютная ошибка в единицах заказов: SMAPE нормирует
отклонение на сумму модулей факта и прогноза.

**Вопрос:** на каком из двух юнитов наивный прогноз с `lag=14` сработал лучше? Можно ли объяснить почему?

:::{dropdown} Ответ
На выбранном 14-дневном тестовом периоде лучше результат у `busier (p75)`: `SMAPE=6.93` против `11.26`
у `typical (p25)`. Среднее арифметическое двух значений — `9.09`.

Сам эксперимент показывает различие в ошибке, но не устанавливает его причину. По двум юнитам и одному
тестовому отрезку нельзя заключить, что более загруженные юниты в целом проще прогнозировать. Для такой
гипотезы нужно проверить другие периоды и больше юнитов, а также сравнить характер колебаний их рядов.
:::

## 3. Итоги

- **`NaiveModel` — baseline**, который использует одну историческую точку. При `lag=1` это последнее известное
  значение, поэтому прогноз на всём горизонте получается постоянным.
- **`lag` — смещение назад, а не размер окна.** `window=1` фиксирован: модель использует одну точку на заданном
  расстоянии от прогнозируемой даты.
- **`context_size` для `NaiveModel` равен `lag`.** Его передают в `make_future(tail_steps=...)`, чтобы подготовить
  достаточный исторический контекст.
- **Для многошагового прогноза полезно правило `lag ≥ horizon`.** Оно не даёт модели использовать собственные
  предсказания внутри горизонта, но не гарантирует минимальную ошибку.
- **Больший `lag` не обязательно лучше.** В эксперименте `lag=14` дал меньший SMAPE, чем `lag=19`, хотя оба
  значения удовлетворяют золотому правилу.
- **Смотри на метрики на нескольких уровнях.** `per-segment` показывает качество по каждому юниту,
  `macro` усредняет сегменты, а `pooled` оценивает совокупную ошибку с учётом масштаба рядов.
